# API 詢問文件產出

協助前端寫一份交給後端的 API 詢問文件。讀者是後端工程師，以及他們交付給 AI agent 閱讀的情境，因此文件要能獨立閱讀、不依賴前端的背景知識。

這個 skill 的核心不是「把格式填滿」，而是兩件事：

1. **查證之後，詢問後端怎麼處理，不直接要求實作。** 前端可以、也應該寫出有根據的查證結論，例如「交付文件中找不到能滿足此情境的 API」。但結論之後的解決方式（新增端點、擴充既有 API、開放既有的內部邏輯等）要交給後端判斷，文件要做的是**詢問後端建議的處理方式**。一旦文件直接寫出解決方案，例如「請新增一支 API」加上契約格式，後端的 AI agent 就會把它當成需求單直接實作，即使標註了「參考、非規定」也擋不住。
2. **每個具體陳述都要有來源。** 文件會被 AI agent 當成事實來讀，一個沒有根據的參數說明，可能讓 agent 去後端程式碼裡找根本不存在的東西，或自己硬做出來。

## 流程

依序進行。需要問使用者時，一次只問一題。

### 步驟 1：確認需求範圍

先向使用者確認：

- 是哪個畫面或功能需要這支 API？前端的使用位置在哪？
- 後端交付文件放在哪裡？（例如 Delivery 目錄、Swagger、Postman collection）
- 有沒有 PM 問答、規格補充、會議紀錄等參考文件？放在哪裡？
- 已經和後端討論過什麼？**確切的共識內容是什麼？**

最後一題很重要。使用者說「跟後端討論後要做成獨立 API」，共識就只有這一句。前端後續的實作細節（觸發時機、提示方式）不能寫成「已與後端確認」。

### 步驟 2：盤點前端使用點

實際讀程式碼，不要憑命名或慣例猜測：

- 呼叫位置、觸發事件、前置條件（什麼情況下會呼叫、什麼情況下不會）
- 目前的 mock 實作與 mock 資料的來源（mock 的內容是誰寫的、有沒有文件依據，用 `git log -S "<文字>"` 追溯）
- 前端目前傳入的參數實際長什麼樣（例如號碼是否含區碼），並記下與理想狀態的落差

### 步驟 3：盤點後端既有交付

判斷這支 API 是否已經存在：

- 在交付目錄全文搜尋相關關鍵字（中英文、同義詞都要搜）。
- **搜尋範圍要涵蓋所有格式。** grep 看不到 docx、pdf、xlsx 的內容，要先轉成文字再搜，例如 docx 可用 `unzip -p file.docx word/document.xml | sed 's/<[^>]*>//g'`，pdf 可用 `pdftotext`。
- **注意 .gitignore。** 參考文件目錄常被忽略，部分搜尋工具（如 ripgrep、ugrep）預設會跳過被忽略的檔案，必要時加上 `--no-ignore` 或改用其他方式確認。
- 端點數量要從實際的端點定義檔數出來，不要憑印象寫。
- 找到「看起來相關」的既有欄位或端點時，確認它是否真的能滿足需求，並記下它不夠用的具體理由。

完成後**先向使用者報告結論**，再決定下一步：

- API 已存在且能滿足需求：說明用法，不需要寫文件。
- 部分滿足或完全不存在：繼續步驟 4，在文件中詢問後端建議的處理方式。

### 步驟 4：撰寫文件

讀取 `references/template.md`，依範本章節撰寫。完整的實例可參考 `references/example-phone-risk-api.md`，但該範例早於「依據與推論的處理原則」，其中標明「推測」後寫進文件的段落（例如對參數意義、欄位用途的推測）不要模仿，應改為直接詢問。

撰寫時同步維護一份**來源清單**（放在自己的工作筆記，不寫進文件）：文件中每個具體陳述（函式名稱、參數、欄位、數字、共識、程式行為）都對應到一個來源，並標示為以下三種之一：

| 等級 | 意義 | 在文件中的寫法 |
|---|---|---|
| 確認 | 有原始來源可以對照（文件原文、實測原始回傳） | 直接陳述，並註明出處 |
| 推測 | 從命名、上下文、少量樣本推論，沒有明確的文字規範，也不足以做嚴謹的因果推導 | **不寫進文件**，只留在工作筆記；改寫成「不清楚」 |
| 不清楚 | 找不到依據，或資料不足以得出結論 | 寫出前端掌握的原始資料，並直接針對模糊的地方發問 |

### 依據與推論的處理原則

後端很可能因為文件中似是而非的說法而敷衍回覆，或被影響判斷，所以文件只能放有依據的內容：

1. **規格書和後端文件都有說明，但互相矛盾**：這是**文件衝突**。兩者並列並附上原文（含出處），請後端說明以哪一份為準或如何處理。不要自行裁定，也不要只引用其中一份。
2. **只有單一資料來源，但資料不足以得到明確的規範或因果關聯**：不能把前端的推論當成提問的前提，也不能寫出推論後請後端確認是否正確。只能列出原始資料，直接問資料模糊或不清楚的地方。
   - 情境：某 API 回傳 `has_discount` 欄位，交付文件沒有說明它的意義；前端從欄位名稱猜測它代表「店家有優惠」，但實測時 `has_discount: true` 的店家查不到任何優惠內容。
   - 錯誤示範：「`has_discount: true` 但查不到優惠內容的店家，應該怎麼處理？」（前提是未經證實的推論：`has_discount` 代表店家有優惠）
   - 正確示範：「請說明 `has_discount` 的判斷依據。」並附上實測原始值。
3. **例外**：只有在有非常明確的文字規範，或足以做嚴謹因果推導時，才能把結論寫成前提，而且要附上依據的原文或推導過程。
4. **實測結果用原始值呈現**（請求與回傳欄位值），不寫「兩版只差在 X」「X 代表 Y」「X 是 Y 加上 Z」這類詮釋。

以下是容易出錯的地方：

- **「沒找到依據」不等於「確認是臆測」。** 下結論前，先確認步驟 3 的搜尋範圍是否完整。找不到出處時，歸為「不清楚」，並寫明搜尋範圍。
- **引用被 gitignore 的文件時，要貼出原文並註明文件標題。** 後端很可能拿不到這些檔案，只寫檔名等於沒有引用。
- **區分「目前程式碼的行為」與「前端打算怎麼做」。** 表格的欄位名稱也要精確，不要讓讀者把計畫誤讀成現況。
- **不要把前端為了測試自行撰寫的 mock 內容（例如提示文字）描述成舊系統或新系統的格式。**

### 步驟 5：查核

分兩輪進行，兩輪都不能省略：

1. **逐條查核**：依來源清單，重新打開每個來源對照一次。特別注意數字、名稱拼寫、共識範圍。
2. **重讀全文**：從頭到尾讀一次，並和程式碼對照。這一輪要抓的是逐條查核抓不到的錯誤，例如欄位名稱語意誤導、前後章節互相矛盾、把計畫寫成現況。

查核完成後，向使用者報告查核結果：哪些已確認、哪些推論已移出文件並改成直接發問、哪些列為文件衝突、這次修正了什麼。如果文件的準確度取決於某份二手資料（例如別人整理的規格落差清單），要明白說出這個限制。

### 步驟 6：交付

- 預設存放在專案的 `docs/backend-requests/YYYY-MM-DD-<topic-slug>.md`，使用者指定其他位置時照使用者的決定。檔名用前端想達成的事命名，不要替 API 取名，否則等於在檔名裡預設了解決方式。
- 告訴使用者完整路徑。如果路徑在隱藏目錄裡（例如 git worktree 的 `.worktrees/`），要提醒使用者 Finder 預設看不到，並可用 `open -R <檔案路徑>` 直接在 Finder 中選取該檔案。
- 依文件的「附件說明」一節，列出使用者需要和文件一起上傳的檔案及其本機完整路徑，分成「一定要附」（A 類）和「視情況附」（B 類）。這些檔案常在被 gitignore 的目錄裡，後端無法從 repo 取得，要提醒使用者直接上傳。

## 撰寫原則

### 前端寫什麼、交給後端決定什麼

| 前端應該寫 | 交給後端決定 |
|---|---|
| 查證結論（例如「交付文件中找不到能滿足此情境的 API」） | 解決方式（新增端點、擴充既有 API、開放既有邏輯…） |
| 前端需要拿到什麼資訊（例如「能分辨查詢失敗和未命中」） | 用什麼方式表達（端點名稱、欄位、錯誤碼、資料結構） |
| 使用情境的特性（呼叫頻率、等待方式、資料來源） | 效能目標、程式結構 |
| 前端已知的線索（程式位置、既有慣例） | 驗收條件（等後端提出方案後，以實測案例為基礎共同訂定） |

### 交付需求（有條件的固定四項）

每份文件都附上以下四項，但要寫成有條件的形式：「**如果後端的建議需要新增或調整 API**，希望交付時附上以下內容」。如果後端已有既定的交付格式（例如固定的交付目錄結構），請後端沿用，不要另外發明新格式：

1. **實際的型別定義**：每個欄位附上意義，以及 `null`／空字串分別代表什麼。
2. **明確的 Request／Response 範例**：涵蓋成功、各種失敗、邊界情境。後端設計中不存在的情境，請直接註明。
3. **Postman 測試案例與實測回傳**：必須是實際執行的結果，不要手寫推測值，因為前端會直接拿它建立 mock data。
4. **API 介接說明**：端點、參數格式、錯誤判斷方式、與既有 API 的關係，以及對應到「前端需要的能力」的方式。

其他交付項目（例如測試環境中可觸發特定結果的測試資料）可以向使用者提議，由使用者決定是否加入。

## 完成前檢查

- [ ] 步驟 3 的搜尋涵蓋了所有檔案格式，也處理了 .gitignore
- [ ] 文件中沒有「已與後端確認」卻超出使用者所說共識範圍的內容
- [ ] 逐句檢查：文件中沒有任何推論（包含問題的前提、實測結果的詮釋、流程圖的節點文字、沒有出處的使用情境描述；符合「依據與推論的處理原則」第 3 條例外、並附上原文或推導過程者除外）；資料不足的地方都改成直接發問
- [ ] 規格書與後端文件互相矛盾的地方，已列為文件衝突，兩者並列並附上原文
- [ ] 查證結論之後，是詢問後端建議的處理方式，沒有直接要求新增 API、沒有附上端點名稱或契約格式
- [ ] 待確認事項的第一題是「後端建議用什麼方式滿足這個需求？」
- [ ] 交付需求寫成有條件的形式，沒有預先訂定的驗收條件
- [ ] 引用 gitignore 文件時，已貼出原文並註明文件標題
- [ ] 附件說明涵蓋了文件中引用的每一份資料，且每份都歸入 A～D 其中一類
- [ ] 重讀全文並和程式碼對照，沒有前後矛盾，也沒有把計畫寫成現況
