# API 詢問文件範本

依序使用以下章節。每一節下方的「寫法說明」只供撰寫時參考，不要寫進最終文件。

章節名稱與順序請維持一致，讓後端每次收到的文件都有相同結構。如果某一節在這次需求中確實不適用（例如沒有舊系統），保留標題並寫一句「不適用」與原因，不要直接刪除。

整份文件的定位是**詢問**：前端說明想達成什麼、查到了什麼，然後請教後端建議怎麼處理。撰寫每一節時，都不要寫出解決方案（例如「請新增一支 API」、端點名稱、契約格式）。

---

```markdown
# [詢問] <前端想達成的事>

> **文件用途**：本文件寫給後端工程師及其 AI 開發助手。前端說明想達成的功能、目前查到的資訊，想請教後端建議的處理方式。
>
> - 提出方：<前端團隊／系統名稱>
> - 日期：<YYYY-MM-DD>
> - 對照基準：<後端交付文件名稱與包含的檔案>
> - 狀態：待後端回覆
```

**寫法說明**：標題寫前端想達成的事，例如「電話號碼風險名單提示的串接方式」，不要寫成「新增某某 API」。「對照基準」要寫出實際查過的檔案。日期只寫能確認的，不要從其他文件間接推得。

---

```markdown
## 閱讀指引
```

**寫法說明**：用表格說明各章節的性質。

| 性質 | 章節 |
|---|---|
| 前端需要的資訊 | 想達成的事、前端需要的能力 |
| 背景（供理解） | 業務背景、現況盤點、前端使用情境、附件說明 |
| 想請教的問題 | 待確認事項 |
| 後續參考 | 交付需求（後端的建議需要新增或調整 API 時才適用）、附錄 |

---

```markdown
## 1. 想達成的事
```

**寫法說明**：一到兩句話，說明前端需要「輸入什麼、得到什麼資訊」，接著說明想請教後端建議如何滿足。不寫欄位名稱，不寫解決方式。

---

```markdown
## 2. 業務背景
### 2.1 舊系統行為
### 2.2 新系統前端目前的實作
```

**寫法說明**：

- 2.1：引用舊系統資料時，貼出原文並註明文件標題。用表格列出「前端掌握程度」，每一項標示為確認、推測或不清楚。
- 2.2：先寫出與後端的**確切共識**，只寫使用者說過已經同意的內容；使用者的說法帶有保留語氣（例如「應該是」）時，照原意呈現，不要寫成確定的共識。如果和後端還沒有共識，就不寫這段，也不要自己湊一段出來，直接用業務依據（例如 PM 的回覆）說明前端實作的根據。接著寫前端依此做的實作，並註明「細節未逐項與後端確認」。前端情境中有業務依據的部分（例如 PM 的回覆），註明出處。
- mock 內容要追溯來源。確認前端自行撰寫的，才寫「沒有文件依據，不代表實際格式」；有出處的，引用原文。

---

```markdown
## 3. 現況盤點：<交付文件名稱> 是否已提供？
### 3.1 查核方式
### 3.2 相關的既有線索
```

**寫法說明**：

- 第一行寫查證結論，例如「前端在交付文件中沒有找到能滿足此情境的 API」。結論之後不要接解決方案。
- 3.1：寫出搜尋的關鍵字、搜尋範圍，以及搜尋結果（包含找到但無關的項目）。列出核對過的端點清單，數量要從端點定義檔實際數出來。
- 3.2：如果有「看起來相關」的既有欄位或端點，貼出實測範例並註明來源，說明前端認為它不符合情境的理由。對它用途的判斷如果只是推測，要明寫。

---

```markdown
## 4. 前端使用情境
```

**寫法說明**：

- 用流程圖畫出觸發條件、各分支（成功、失敗、不呼叫的情況）。
- 列出影響後端判斷的使用特性：呼叫頻率、使用者是否需要等待、資料來源與格式。
- 列出目前的 mock 實作位置。
- 前端已知的落差（例如目前傳入的參數格式不理想），寫成「前端已知待修」，並附具體例子，說明後端不必遷就。

---

```markdown
## 5. 前端需要的能力
```

**寫法說明**：用表格列出 N1、N2… 每一項包含「前端需要做到什麼」與「為什麼需要」。只寫前端需要拿到的資訊，不寫後端該怎麼給。

常見的能力項目（依需求取捨）：

- 能明確判斷結果（例如命中／未命中、成功／失敗）
- 能拿到可以直接顯示的內容
- 能分辨「查詢失敗」和「沒有資料」，避免系統錯誤被誤判為正常結果
- 重複呼叫不會造成業務副作用
- 回應速度不會明顯影響使用者操作

---

```markdown
## 6. 待確認事項
```

**寫法說明**：表格欄位只有「#」「問題」。不要附上前端的暫定假設或預設答案：它既不是前端目前的實作，也提供不了任何資訊，反而容易讓讀者誤以為是現況或前端的期望。

- **Q1 固定為「後端建議用什麼方式滿足這個需求？」**。其餘問題是細節，放在 Q1 之後，並以「如果後端的建議是…」這類條件句提問，不預設方案。
- 已經能從既有文件（例如後端先前的回覆、交付文件）找到答案的問題，不要再問，改寫成正文中的已知事實並註明出處。
- 問題用開放式問法，不要在問題裡預設答案。
- 可能需要業務方決定的問題，要註明。
- 最後一題固定為「如果需要新增或調整 API，預計在哪一次交付？」

---

```markdown
## 7. 交付需求（後端的建議需要新增或調整 API 時）
### 7.1 實際的型別定義
### 7.2 明確的 Request／Response 範例
### 7.3 Postman 測試案例與實測回傳
### 7.4 API 介接說明
```

**寫法說明**：開頭寫明「如果後端的建議需要新增或調整 API，為了讓前端快速理解回傳結果，並以最快速度套用到目前專案，希望交付時附上以下內容」，並請後端沿用既有的交付格式。各小節內容見 SKILL.md 的「交付需求（有條件的固定四項）」。7.2 用表格列出需要的情境，並註明「後端設計中不存在的情境，請直接註明」。

---

```markdown
## 附錄：參考線索（供後端 AI agent 參考）
```

**寫法說明**：只列前端掌握的線索，例如服務名稱、既有路由慣例、舊系統程式位置、可能相關的既有實作。每一項都註明來源；來自二手資料的，註明「前端未核對原始碼」。不寫後端該怎麼實作。

---

```markdown
## 附件說明
### A. 隨本文件附上
### B. 後端交付文件（視情況附上）
### C. 前端程式碼（未附上）
### D. 前端沒有的文件（無法附上）
```

**寫法說明**：把文件中引用的**每一份**資料歸到四類之一，讓後端知道手上拿到了什麼、缺了什麼。開頭註明「附件以檔名識別，不保留原本的目錄結構」，因為文件常經由 Slack 等管道平鋪上傳。

- **A. 隨本文件附上**：後端手上可能沒有、而文件內容依賴它的資料，通常是前端整理的規格文件、PM 回覆紀錄、被 gitignore 的參考文件。每一份寫出內容摘要、在文件中的引用處。如果只引用了其中一部分，要指出是哪幾段，並說明其餘段落與本需求無關。
- **B. 後端交付文件**：後端自己交付過的檔案。寫明「如果本次沒有附上，代表後端環境已經有，請以手邊的版本為準」，讓文件不論有沒有附都不需要修改。附上每份檔案在交付目錄中的位置。只是在搜尋結果中順帶提到、與需求無關的檔案，另外用一句話交代即可，不列入表格。
- **C. 前端程式碼**：不附上，並標出相關內容在文件的哪一節已經描述過。如果某段程式碼的內容沒有在文件中描述，就應該先補進文件正文，而不是改成附上程式碼。
- **D. 前端沒有的文件**：例如舊系統原始碼、只被轉引的原始規格書。註明文件中相關內容是從哪份附件轉引的，並請後端以原始內容為準。

某一類如果沒有任何項目，保留標題並寫「無」。
