# API 需求文件範本

依序使用以下章節。每一節下方的「寫法說明」只供撰寫時參考，不要寫進最終文件。

章節名稱與順序請維持一致，讓後端每次收到的文件都有相同結構。如果某一節在這次需求中確實不適用（例如沒有舊系統），保留標題並寫一句「不適用」與原因，不要直接刪除。

---

```markdown
# [需求] <後端服務名稱> 新增「<API 功能名稱>」API

> **文件用途**：本文件寫給後端工程師及其 AI 開發助手。可直接把整份文件交給 AI agent，讓它了解這支 API 的使用情境，以及前端需要拿到哪些資訊，再由後端依自己的架構設計與實作。
>
> - 提出方：<前端團隊／系統名稱>
> - 日期：<YYYY-MM-DD>
> - 對照基準：<後端交付文件名稱與包含的檔案>
> - 狀態：待後端確認與排程
```

**寫法說明**：「對照基準」要寫出實際查過的檔案。日期只寫能確認的，不要從其他文件間接推得。

---

```markdown
## 閱讀指引：哪些是需求、哪些是參考
```

**寫法說明**：用表格把各章節分成三類，並加一段給 AI agent 的提醒：「參考」類章節不是規格，與後端架構衝突時以後端判斷為準。

| 性質 | 章節 |
|---|---|
| 需求（請滿足） | 一句話需求、前端需要的能力、交付需求 |
| 背景（供理解） | 業務背景、現況盤點、前端使用情境、附件說明 |
| 參考（可自由調整） | 參考格式、待確認事項、附錄 |

---

```markdown
## 1. 一句話需求
```

**寫法說明**：一到兩句話，只講「輸入什麼、得到什麼資訊」。不寫欄位名稱，不寫實作方式。

---

```markdown
## 2. 業務背景
### 2.1 舊系統行為
### 2.2 新系統前端目前的實作
```

**寫法說明**：

- 2.1：引用舊系統資料時，貼出原文並註明文件標題。用表格列出「前端掌握程度」，每一項標示為確認、推測或不清楚。
- 2.2：先寫出與後端的**確切共識**，只寫使用者說過已經同意的內容。接著寫前端依此做的實作，並註明「細節未逐項與後端確認」。
- mock 內容如果是前端自行撰寫，要明確說明「沒有文件依據，不代表實際格式」。

---

```markdown
## 3. 現況盤點：<交付文件名稱> 是否已提供？
### 3.1 查核方式
### 3.2 相關的既有線索
```

**寫法說明**：

- 第一行直接寫結論。
- 3.1：寫出搜尋的關鍵字、搜尋範圍，以及搜尋結果（包含找到但無關的項目）。列出核對過的端點清單，數量要從端點定義檔實際數出來。
- 3.2：如果有「看起來相關」的既有欄位或端點，貼出實測範例並註明來源，說明為什麼它不夠用。對它用途的判斷如果只是推測，要明寫。

---

```markdown
## 4. 前端使用情境
```

**寫法說明**：

- 用流程圖畫出觸發條件、各分支（成功、失敗、不呼叫的情況）。
- 列出影響後端設計的使用特性：呼叫頻率、使用者是否需要等待、資料來源與格式。
- 列出目前的 mock 實作位置。
- 前端已知的落差（例如目前傳入的參數格式不理想），寫成「前端已知待修」，並附具體例子，說明後端不必遷就。

---

```markdown
## 5. 前端需要的能力
```

**寫法說明**：用表格列出 N1、N2… 每一項包含「前端需要做到什麼」與「為什麼需要」。只寫前端需要拿到的資訊，不寫後端該怎麼給。

最後加上：「正式驗收條件：等後端確認 API 契約後，以後端提供的實測案例為基礎，由前後端共同補上。本文件不預先訂定。」

常見的能力項目（依需求取捨）：

- 能明確判斷結果（例如命中／未命中、成功／失敗）
- 能拿到可以直接顯示的內容
- 能分辨「查詢失敗」和「沒有資料」，避免系統錯誤被誤判為正常結果
- 重複呼叫不會造成業務副作用
- 回應速度不會明顯影響使用者操作

---

```markdown
## 6. 參考格式（非規定）
```

**寫法說明**：開頭寫明「以下只為說明第 5 節需要哪些資訊，端點名稱、欄位名稱、結構、錯誤處理方式都請依後端設計決定」。每個範例用註解標出它對應第 5 節的哪一項。格式可沿用後端既有的回應慣例，方便閱讀。

---

```markdown
## 7. 待確認事項
```

**寫法說明**：表格欄位為「#」「問題」「後端回覆前前端的暫定假設」。表格上方說明：暫定假設不是前端目前程式碼的行為，也不代表前端希望後端這樣做。

- 問題用開放式問法，不要在問題裡預設答案。
- 可能需要業務方決定的問題，要註明。
- 最後一題固定為「預計在哪一次交付？」

---

```markdown
## 8. 交付需求
### 8.1 實際的型別定義
### 8.2 明確的 Request／Response 範例
### 8.3 Postman 測試案例與實測回傳
### 8.4 API 介接說明
```

**寫法說明**：開頭寫明「為了讓前端快速理解回傳結果，並以最快速度套用到目前專案」，並請後端沿用既有的交付格式。各小節內容見 SKILL.md 的「交付需求（固定四項）」。8.2 用表格列出需要的情境，並註明「後端設計中不存在的情境，請直接註明」。

---

```markdown
## 附錄：參考線索（供後端 AI agent 參考，非規定）
```

**寫法說明**：只列前端掌握的線索，例如服務名稱、既有路由慣例、舊系統程式位置、可能相關的既有實作。每一項都註明來源；來自二手資料的，註明「前端未核對原始碼」。不寫後端該怎麼實作。

---

```markdown
## 附件說明
### A. 隨本文件附上
### B. 後端交付文件（視情況附上）
### C. 前端程式碼（未附上）
### D. 前端沒有的文件（無法附上）
```

**寫法說明**：把文件中引用的**每一份**資料歸到四類之一，讓後端知道手上拿到了什麼、缺了什麼。開頭註明「附件以檔名識別，不保留原本的目錄結構」，因為文件常經由 Slack 等管道平鋪上傳。

- **A. 隨本文件附上**：後端手上可能沒有、而文件內容依賴它的資料，通常是前端整理的規格文件、被 gitignore 的參考文件。每一份寫出內容摘要、在文件中的引用處。如果只引用了其中一部分，要指出是哪幾段，並說明其餘段落與本需求無關。
- **B. 後端交付文件**：後端自己交付過的檔案。寫明「如果本次沒有附上，代表後端環境已經有，請以手邊的版本為準」，讓文件不論有沒有附都不需要修改。附上每份檔案在交付目錄中的位置。只是在搜尋結果中順帶提到、與需求無關的檔案，另外用一句話交代即可，不列入表格。
- **C. 前端程式碼**：不附上，並標出相關內容在文件的哪一節已經描述過。如果某段程式碼的內容沒有在文件中描述，就應該先補進文件正文，而不是改成附上程式碼。
- **D. 前端沒有的文件**：例如舊系統原始碼、只被轉引的原始規格書。註明文件中相關內容是從哪份附件轉引的，並請後端以原始內容為準。

某一類如果沒有任何項目，保留標題並寫「無」。
