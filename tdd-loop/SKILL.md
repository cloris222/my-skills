# TDD 自動化循環 (tdd-loop)

## 觸發時機

當用戶要求「寫測試」、「補測試」、「為某功能加測試」、「測試一條龍」時使用。

**開始前**：先呼叫 `superpowers:test-driven-development` skill，確認 TDD 核心原則已載入。

---

## 鐵律（不可違反）

```
1. 測試檔案一旦寫定，不得修改來使測試通過
2. 測試失敗時，只能修改實作程式碼
3. 不得刪除測試或降低斷言強度
4. 必須先診斷失敗原因，才能動手修改
5. 若判斷測試本身有誤，必須向用戶說明並獲得確認，才能修改測試
```

違反以上任一條 → 停止，向用戶說明，等待指示。

---

## 執行流程

### Phase 0：確認範圍

開始前確認以下三點：

1. **測試目標**：哪個函式 / 元件 / 功能？
2. **測試框架與指令**：
   - 預設使用 Vitest：`npx vitest run [檔案路徑]`
   - 全部測試：`npx vitest run`
3. **完成條件**：所有新增測試通過，且未破壞既有測試

若有不清楚的地方，先詢問用戶再繼續。

---

### Phase 1：寫測試（RED）

依照 `superpowers:test-driven-development` 的原則撰寫測試：

- 每次只寫**一個行為**的測試
- 測試名稱描述行為，不描述實作
- 優先使用真實程式碼，避免不必要的 mock
- 寫完後執行測試，**確認是紅燈**

```bash
npx vitest run path/to/target.test.js
```

紅燈確認後，進入 Phase 2。

---

### Phase 2：自我修正循環（GREEN）

```
最大嘗試次數：5 次

loop:
  step 1. 診斷失敗原因
          - 說明：為什麼失敗？錯誤訊息代表什麼？
          - 不可跳過此步驟

  step 2. 修改實作程式碼
          - 只動實作檔案，不動測試檔案
          - 修改範圍最小化，不順手重構無關的程式碼

  step 3. 執行測試
          npx vitest run path/to/target.test.js

  step 4. 判斷結果
          ✅ 全過 → 進入 Phase 3
          ❌ 仍失敗 → 回到 step 1
          🔄 嘗試次數已達 5 次 → 進入 Phase 4
```

每次循環結束後，輸出簡短狀態報告：

```
[嘗試 N/5] 測試狀態：X/Y 通過
診斷：[本次失敗原因]
修正：[本次修改了什麼]
```

---

### Phase 3：重構（REFACTOR）

測試全數通過後：

1. 執行全部測試，確認無既有測試被破壞：
   ```bash
   npx vitest run
   ```
2. 進行重構（整理命名、去除重複），不改變行為
3. 重構後再次執行全部測試，確認仍為綠燈
4. 輸出完成報告：已測試的行為清單、覆蓋的 edge case

---

### Phase 4：卡關升級

嘗試 5 次仍未通過時，向用戶報告：

```
⚠️ 自我修正達到上限（5 次），需要確認

目前失敗的測試：
- [測試名稱]：[失敗原因]

已嘗試的修正：
1. [修正描述]
2. [修正描述]
...

卡關原因分析：
[可能的根本原因或設計問題]

請問要如何繼續？
A. 調整實作方向（請說明）
B. 確認測試本身是否需要修改
C. 暫停並人工介入
```

等待用戶確認後再繼續。

---

## 測試優先順序（本專案）

在不確定從哪裡開始時，依以下順序：

1. `src/method/` — 純邏輯函式，最容易測試
2. `src/stores/` — Pinia store 的狀態邏輯
3. 單一頁面的互動邏輯（`src/views/`）
4. 元件行為（`src/components/`）

---

## 完成條件

以下全部達成才算完成：

- [ ] 所有新增測試通過（綠燈）
- [ ] 既有測試未被破壞
- [ ] 測試覆蓋目標行為的 happy path 與主要 edge case
- [ ] 測試程式碼未被修改（除非用戶明確確認）
- [ ] `npx vitest run` 輸出乾淨，無 warning/error
